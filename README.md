# AI Hiking Health Coach

산행 기록을 학습해 다음 산행을 추천하는 **AI 등산 코치**.

> **이 저장소의 현재 상태**
> 최종 서비스가 아니다. 다른 AI 가 만든 웹 프로토타입을 출발점으로, **모바일 앱을 중심에 둔
> 확장 가능한 개발 기반을 준비하는 단계**다. 기능 요구사항은 아직 확정되지 않았고,
> 이 문서에서 **⏸ 로 표시된 항목은 결정되지 않은 사항**이다.

---

## 1. 제품 구성 — 모바일 Primary

```
Primary    모바일 앱   핵심 제품. 실제 산행 경험이 일어나는 곳
Backend    서버        계정 · 데이터 저장/동기화 · AI/추천
Secondary  웹          현재는 소개 · 시연 우선. 역할 확대 가능성은 열어둠
```

**모바일을 Primary 로 두는 이유** — 이 서비스의 핵심은 산행 중 현재 위치와 **실제 이동 경로를
기록하는 것**이다. 산행은 3~5시간이고 그동안 사용자는 휴대폰을 보지 않는다. 화면이 꺼지면
위치 수집이 멈추는 웹(iOS 에서 백그라운드 위치 수집 불가)으로는 이 기능이 성립하지 않는다.

그래서 아래 기능은 **네이티브 런타임을 전제로 판단**한다.

- 백그라운드 GPS · 실제 이동 경로 기록
- 오프라인 동작 (산에는 신호가 없다)
- 기압계 기반 고도, Apple Health / Health Connect, 워치 컴패니언
- 그룹 산행 위치 공유

**웹의 기능 분담은 지금 확정하지 않는다.** 서비스 방향에 따라 역할이 커질 수 있으므로,
"웹은 여기까지만" 이라고 고정하지 않는다.

### ⏸ 미정 — 모바일 기술 스택

Expo / React Native / Capacitor / Flutter 중 무엇을 쓸지 정하지 않았다.
아래 질문의 답에 따라 결정한다.

- 워치 연동이 "실시간 심박" 인가 "산행 후 데이터 읽기" 인가
- 그룹 위치 공유가 1단계 범위인가 장기 과제인가
- 워치 연동이 Apple Health / Health Connect 읽기인가, Garmin/Fitbit 클라우드 API 인가

스택이 무엇이 되든 **`packages/core` 는 그대로 재사용된다** — 그것이 core 를 먼저 분리한 이유다.

## 3. 실행

```bash
npm install
npm run dev       # core 자동 빌드 → http://127.0.0.1:5173
npm run check     # 순수성 + 타입 + 회귀 테스트
```

| 스크립트 | 동작 |
|---|---|
| `dev` | Vite 개발 서버 (HMR) |
| `build` | `dist/` 생성 |
| `preview` | 빌드 산출물 서빙 |
| `smoke` | jsdom 회귀 테스트 (19개 검사) |
| `check` | `core:purity` + `core:typecheck` + `smoke` |
| `core:build` | core 번들 + 타입 선언 |

`predev` / `prebuild` / `presmoke` 가 core 를 먼저 빌드하므로 순서를 신경 쓸 필요는 없다.

> `file://` 로 직접 열면 안 된다. `localStorage` 가 막히고 CDN 로드가 불안정하다.

## 4. 현재 구현되어 있는 것

**웹 프로토타입으로 동작하는 화면 15개.** UI 는 프로토타입 단계이며 리디자인 대상이다.

| 흐름 | 라우트 |
|---|---|
| 첫 진입 | `splash` → `intro` → `onboard` (4문항 + 기본정보) → `first-recommend` |
| 홈 | `home` |
| 추천 | `recommend` → `course-detail` |
| 산행 | `hiking-setup` → `hiking-live` → `hike-result` → `analysis` |
| 기록 | `records` → `record-detail` / `patterns` |
| 마이 | `profile` |

동작하는 순환 구조:

```
산행 완료 → 기록 추가 → 통계 재계산 → 분석 갱신 → 다음 추천 변경
```

화면의 숫자는 박아넣은 값이 아니라 저장된 기록에서 계산된다. 데이터가 없으면 **없는 값을
지어내지 않고 "없음" 으로 표시**한다 — 이것이 이 프로젝트에서 유지하는 원칙이다.

### 시뮬레이션 · mock 인 것 (실제 연동 아님)

| 항목 | 현재 상태 |
|---|---|
| GPS · 산행 진행 | `setInterval` 기반 시뮬레이션. 코스 고도 프로파일을 따라 보간 |
| 페이스 안정성 | `Math.random()` 으로 생성 |
| 날씨 조건 | mock 제공자 (기온 · 강수 등 고정값). **날짜는 예정일에서 계산** |
| 등산로 경로 지도 | 코스와 무관한 고정 SVG. 현재 위치 마커도 움직이지 않음 |
| 코스 카탈로그 | 하드코딩 10개 |
| 서버 · 계정 · 동기화 | 없음. `localStorage` 단일 키 `hhc.state.v1` |

### 디자인 시스템

색 · radius · shadow · 타이포 · 모션이 전부 `css/tokens.css` 의 CSS 변수로 제어된다.
테마 프리셋 5종(Forest Green / Deep Forest / Navy Trail / Slate Minimal / Midnight)과
Primary/Secondary 색상 · 버튼 형태를 **마이 화면의 디자인 시스템 콘솔에서 즉시 변경**할 수 있다.

> 모바일 Primary 전제에서는 토큰의 원본이 CSS 가 아니라 **플랫폼 중립 값**이어야 한다.
> `tokens.css` 의 값 자체는 재사용하되, 원본 위치 이동은 ⏸ 검토 예정.

## 5. 결정되어 반영된 것

| | 결정 | 반영 |
|---|---|---|
| 날짜 기준 | **Asia/Seoul 고정** | 기록별 timezone 저장 안 함, GPS timezone 처리 안 함. 오늘/어제 판정은 한국 달력일 기준 |
| "개인화 활성화" 단계 | **개념 제거** | 온보딩 정보로 첫 산행부터 개인화한다. 3단계 상태(`stage`)와 `count>=3` 단일 게이트를 삭제하고, **기능별 최소 데이터 조건**으로 대체 |
| 산행 간격과 난이도 | **간격을 난이도 결정 근거로 쓰지 않음** | "평소보다 오래 쉬었으면 난이도 하향" 로직과 관련 문구 삭제. 간격은 학습된 패턴 표시 · 계획 참고용으로만 남음 |
| 산행 예정일 | **온보딩 예정 시점에서 파생 + 사용자 지정 가능** | 예보 범위(10일)를 넘으면 날씨를 만들어내지 않고 "예보 없음" |
| 차트 | 좌표 계산은 core, 렌더는 플랫폼 | 모바일이 `react-native-svg` 로 같은 좌표를 그릴 수 있다 |
| 아이콘 | 의미 키(`'trend-up'`) + 플랫폼 매핑 | core 가 Font Awesome 에 묶이지 않는다 |
| 데모 시드 | 개발 전용 별도 번들 | 프로덕션에서 스크립트 2곳만 빼면 제외된다 |

## 6. ⏸ 아직 결정되지 않은 것

**이 절의 항목은 구현하지 않는다.** 전체 목록은 [`docs/ISSUES.md`](docs/ISSUES.md) 의
"보류 중" 색인에 있다.

### 6-1. 추천 로직의 정책

현재 `recommendNext()` 에 **동작하는 구현이 있지만, 그 정책은 확정된 것이 아니다.**
프로토타입에서 이어받은 계산식이며, 아래가 미결정이다.

- **이전 산행 결과가 다음 추천 난이도에 영향을 주는가** — 현재 코드는 평균 난이도와
  체력 추세를 통해 영향을 주고 있다. 이는 명시적 규칙이 아니라 평균·추세 계산의 부작용이며,
  유지 여부가 정해지지 않았다
- 스코어링 계수(난이도 차 ×26, 거리 차 ×30, 재방문 감점 …) 는 튜닝 근거가 없는 하드코딩
- "분석 신뢰도 %" 는 기록 개수의 선형 함수일 뿐이다

### 6-2. 산행 목표 지점 구조

정리된 방향만 있고 **데이터 모델과 추천 반영 방식은 미정**이다.

방향으로 확인된 것:

- 각 산행은 기본적으로 독립적이다. 정상까지 못 갔다는 이유로 다음 난이도를 자동으로 낮추지 않는다
- "중도 하산" 과 "목표 미달성" 은 같지 않다
- 사용자 흐름 순서는 **산행지/코스 선택 → 이번 산행의 목표 설정 → 산행** 이다.
  목표 지점은 코스 선택의 입력이 아니라 코스 선택 이후의 단계다
- **목표 지점이 코스 난이도를 바꾸지 않는다.** 코스 난이도와 "이번 산행의 예상 수행 부담" 은
  별도 개념으로 검토한다 (현재 코드에는 코스 난이도 개념만 존재한다)

미정: 목표 지점의 데이터 모델 · 추천 단위 · 난이도 영향 여부 · 두 난이도 개념의 정의

완주율 기반 정책(30% 미만 저장 안 함, `aborted` 플래그로 통계 제외 등)은 **적용하지 않는다.**

### 6-3. 스키마 · 마이그레이션 — 일괄 처리 전

**개별 이슈를 결정하는 즉시 스키마를 바꾸지 않는다.** 관련 이슈 전체의 검토와 요구사항
결정이 끝난 뒤 **한 번에** 정리한다. 현재 코드의 스키마에 맞추려고 필드를 미리 추가하지 않는다.

한 번에 처리할 대상:

- `Course.duration`(분)과 `HikeRecord.duration`(초) 단위 불일치
- 기록마다 코스의 고도 배열을 복사 저장하는 중복
- 스키마 버전 · 마이그레이션 로직 부재 (현재 `mergeState` 는 얕은 병합)
- 산행 목표 지점 관련 필드
- 코스 데이터를 서버 기반으로 옮길 때의 모델 분해

### 6-4. 그 밖의 미정

- AI 분석 문구 생성 방식 (규칙 엔진 유지 / LLM / 하이브리드) — 로직 정리 후 판단
- "예보 없음" 이 기본 표시가 되는 것을 그대로 둘지
- 산행 예정일 선택 UI 의 위치 (이동 가능한 구조로 구현되어 있음)
- 웹의 기능 분담 범위

## 7. 데이터 연동 조사 현황

조사만 완료했고 **연동은 하지 않았다.** 상세: [`docs/RESEARCH-map-and-trail-data.md`](docs/RESEARCH-map-and-trail-data.md)

### 지도 — 카카오맵 API

| | |
|---|---|
| 가능 | Web(JS) · Android v2 · iOS v2 SDK. 지도 표시 · 위치 · 경로 오버레이 |
| 불가 / 제약 | 등산로 노선 데이터를 제공하지 않는다. **오프라인 지도 미지원**, 응답 데이터 캐싱 정책 제한 |
| 쿼터 | 2026-07-21 변경 — 계정당 첫 활성화 앱만 무료. 신규 경로/정적지도 API 일 1,000건 |
| ⏸ 미정 | 지도 제공자 최종 선택 (카카오맵 / V-World / 국토지리정보원). 모바일 스택 결정과 함께 |

설계 방향으로 정리된 것: **지도 타일은 온라인 전용 · 교체 가능한 레이어로 취급하고,
등산로 노선 · 지점 · 고도는 우리 데이터로 보관**한다. 그러면 신호가 없어도 경로와 내 위치를
그릴 수 있고, 지도 제공자를 바꿔도 핵심 기능이 흔들리지 않는다.

### 등산로 — 공공데이터

확보 가능하다는 것까지 확인했다.

| 데이터 | 내용 |
|---|---|
| **산림청 전국등산로표준데이터** (1순위) | SHP·JSON·GPX / 2,919행 / 무료 / **이용허락범위 제한 없음**. 거리 · 소요시간 · 난이도 · 편의시설 · 접근성 포함 |
| 산림청 등산로정보 | 산별 GPX/SHP/JSON 개별 다운로드 |
| 국립공원공단 | 선형시설(탐방로) · 다목적위치표지판(위치 + 고도) |
| 산 마스터 | 100대명산 목록(위경도 · 해발고도) · 산정보 서비스 |
| 고도 | 국토지리정보원 DEM · GPX `<ele>` |
| 배경지도 대안 | V-World(등산로 포함) · 국토지리정보원 WMTS |

주의: **통제 · 폐쇄 여부와 추천구간은 실시간 반영되지 않는다.** 안전 기능에 그대로 쓸 수 없다.

연동 전 확인 필요: 실제 필드명 · 난이도 체계 · **좌표계(WGS84 변환 필요 가능성)** ·
GPX 고도 포함 여부 · 좌표 밀도 · 각 플랫폼 약관.

### 날씨

현재 mock 제공자를 쓴다. core 는 날씨를 **주입받는 구조**이므로
실제 API 를 붙일 때 core 를 수정하지 않는다 (제공자만 교체).
⏸ 어느 API 를 쓸지는 미정.

## 8. 품질 장치

```
npm run check
  core:purity      core 에 브라우저 전용 API 가 없는지 (14종 검사)
  core:typecheck   TypeScript strict
  smoke            jsdom 에서 앱을 부팅해 19개 검사
```

회귀 테스트가 검사하는 것 — 15개 라우트 렌더(2개 상태) · 산행 순환 루프 · 기록 삭제 후
재계산 · 테마 5종 · 예정일 해석 · **산행 간격이 난이도에 영향 없음** · **기능별 데이터 조건** ·
**날짜 KST 고정** · 차트 기하 골든값 · SVG id 유일성 · 아이콘 매핑 · 파생값 캐시 정합성 ·
데모 번들 분리 · 전역 오염 없음.

결정 사항 중 **되살아나면 안 되는 것들**(간격 기반 난이도, 단계 개념, 제거된 문구)은
테스트가 직접 검사한다.

리팩터링할 때는 이전 커밋과 렌더 결과를 비교해 **의도한 곳만 바뀌었는지** 확인해 왔다.

## 10. 기술 스택

| | |
|---|---|
| 도메인 코어 | TypeScript (strict), 플랫폼 의존 0 |
| 웹 | Vanilla JS + CSS 변수 토큰, 프레임워크 없음 |
| 빌드 · 개발 서버 | Vite 7, npm workspaces |
| 테스트 | jsdom (회귀 스모크) |
| 외부 의존 | Google Fonts, Font Awesome 6 (CDN). JS 라이브러리 없음 |
| 저장 | `localStorage` (⏸ 서버 도입 예정) |
| 이미지 | CC/PD 라이선스 산행 풍경 |

웹의 프레임워크 전환(React/TypeScript 등)은 ⏸ 미정이다. 기능 요구사항이 확정된 뒤
UI 계층을 결정한다. 그때까지 도메인 로직을 core 에 모아 두는 것이 이 단계의 목표다.
